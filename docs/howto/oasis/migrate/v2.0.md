# Migrate to NOMAD 2.0

## Upgrading an Oasis from 1.4.3 to 2.0.x

Updating the distribution from [template v1.4.3](https://github.com/FAIRmat-NFDI/nomad-distro-template/tree/v1.4.3) to [template v2.0.0](https://github.com/FAIRmat-NFDI/nomad-distro-template/tree/v2.0.0) changes both the NOMAD stack (1.4.3 → 2.0) and Elasticsearch (7 → 9). **Merging the template alone does not migrate your search index.** NOMAD 1.4.3 only supports ES7, and the new template starts ES9 with a separate, initially empty volume.

For an existing Oasis, use this order:

1. Complete **Before You Start** below while the old deployment is still available.
2. Stop the old stack and copy its entries index to a separate ES9 volume using the standalone migration Compose file in **Option 1 (recommended)**. Keep NOMAD services stopped during the copy.
3. Only after verifying the copy, switch the main Elasticsearch service to the migrated ES9 volume and start NOMAD 2.0.x, as described in **Finalize the Migration**.

Follow the template's [updating the distribution instructions](https://github.com/FAIRmat-NFDI/nomad-distro-template/tree/v2.0.0#updating-the-distribution-from-the-template) to merge the application, Dockerfile, workflow, and configuration changes, but do not run a full `docker compose up -d` until the Elasticsearch migration is complete. Build and pull your updated distribution image with the intended NOMAD 2.0.x version and compatible plugins before starting the upgraded stack.

## Elasticsearch Migration (v7.17 to v9.5)

Starting with **NOMAD 2.0**, the default Elasticsearch image has been changed from **Elasticsearch 7** to **Elasticsearch 9** (default container version `9.5.0`).

Because Elasticsearch 9 cannot read indices created with Elasticsearch 7 due to major Lucene version changes, existing data cannot be read directly from an old Elasticsearch 7 volume.

There are two migration options:

1. **Option 1: Reindex data directly from ES7 to ES9 (running two containers, recommended)** — Runs ES9 alongside ES7 and copies the existing index through Elasticsearch's remote `_reindex` API (an index copy, not NOMAD upload reindexing). This is usually faster because it copies indexed documents without reprocessing archive files. As a rough benchmark, migrating a project with 10,000 perovskite entries took about 1 minute with Option 1 and 15 minutes with Option 2 on the same machine.
2. **Option 2: Start with a fresh ES9 index and reindex uploads** — Discards the ES7 search index and rebuilds it from MongoDB and the archive files (`.volumes/fs`), which are NOMAD's source of truth. This is simpler but can be considerably slower because NOMAD must read and index every upload again.

!!! note
    Previously, NOMAD maintained a separate materials index (`nomad_materials_v1` / `nomad_oasis_materials_v1`). This index is deprecated and dropped in NOMAD 2.0. **Only the entries index (`nomad_oasis_entries_v1` or `nomad_entries_v1`) needs to be migrated.**

### Before You Start

Run these commands from your Oasis deployment directory. You will need `jq` on the host for the configuration checks below. Option 1 uses `curl` inside the Elasticsearch containers. Both options require downtime and a verified backup of MongoDB, `.volumes/fs`, and your deployment configuration. The template provides `bash scripts/backup-mongo.sh`; check that its database name matches your deployment before using it.

The [v2.0.0 distribution template](https://github.com/FAIRmat-NFDI/nomad-distro-template/tree/v2.0.0) already uses Elasticsearch `9.5.0`, container name `nomad_oasis_elastic_9`, and volume name `nomad_oasis_elastic_9`. It also sets `NOMAD_ELASTIC_VERSION: ${NOMAD_ELASTIC_VERSION:-9}` in the shared `x-nomad-environment` anchor. The steps below describe migrating an existing ES7 deployment, not a fresh installation.

!!! warning
    Do not start ES9 with your ES7 data volume or mount the same data volume in two Elasticsearch containers at once. For Option 1, the standalone migration Compose file starts ES7 on the old volume and ES9 on a separate volume. Never use `docker compose down -v` during migration, as it removes named volumes.

Before changing the deployment, record the effective entries index name and the actual ES7 volume name:

```bash
INDEX="$(docker compose exec -T app python -c 'from nomad.config import config; print(config.elastic.entries_index)')"
printf 'Entries index: %s\n' "$INDEX"
docker inspect "$(docker compose ps -q elastic)" | \
  jq -r '.[0].Mounts[] | select(.Destination == "/usr/share/elasticsearch/data") | .Name // .Source'
```

Keep the same `INDEX` value throughout the migration and in the upgraded NOMAD configuration. The template uses `nomad_oasis_entries_v1`; NOMAD's fallback is `nomad_entries_v1`, and custom deployments may use other names. If needed, set `NOMAD_ELASTIC_ENTRIES_INDEX` in the shared `x-nomad-environment` anchor for all NOMAD services. The template bakes `configs/nomad.yaml` into the image; editing that file locally only affects running services if you rebuild the image or enable its bind mount in `x-nomad-base`.

Stop incoming requests and all services that can modify entries before copying or rebuilding the index. In a standard deployment:

```bash
docker compose stop proxy north app worker
```

Also stop any optional CPU/GPU workers or external writers. Run Option 1's commands in the same Bash shell so that `INDEX` and the `MIGRATION` command array remain set.

### Option 1: Reindex data directly from ES7 to ES9 (running two containers)

This approach starts ES9 from your main Compose file and uses a separate, temporary Compose project containing only the ES7 source. Both containers join the main stack's Docker network. Elasticsearch's remote `_reindex` API copies the indexed documents without running NOMAD services.

#### 1. Start the Temporary Migration Environment

After completing **Before You Start**, stop the old stack using its original Compose configuration, **before merging the updated template**:

```bash
docker compose down
```

Keep the recorded entries index name, old volume name, and backups. If you have already merged the template, ensure all old containers are stopped before continuing. Never restart NOMAD against the empty ES9 index.

Merge the updated distribution template now, keeping NOMAD services stopped. Use its main `docker-compose.yaml` for ES9 and `docker-compose.es-migration.yaml` for the temporary ES7 source. The migration file is standalone: do not merge it into `docker-compose.yaml` or pass both files with `-f`.

The main file must include this setting under `services.elastic.environment` (included in the updated template), allowing remote copying only when explicitly enabled:

```yaml
- reindex.remote.whitelist=${ELASTIC_REINDEX_REMOTE_WHITELIST:-}
```

Ensure the main `elastic` service uses ES9 and the separate `nomad_oasis_elastic_9` volume. Set the actual old Docker volume name recorded earlier, enable the ES7 remote source, and start **only Elasticsearch** from each project:

```bash
export ES7_VOLUME=nomad_oasis_elastic # Replace with your recorded old volume name.
# If your deployment uses another ES7 image version, retain it:
# export ES7_IMAGE=docker.elastic.co/elasticsearch/elasticsearch:7.17.28
export ELASTIC_REINDEX_REMOTE_WHITELIST=elastic_7:9200
MIGRATION=(docker compose -p nomad-es-migration -f docker-compose.es-migration.yaml)
docker compose config --quiet
"${MIGRATION[@]}" config --quiet
# Creates the main stack's network and starts ES9, without the app or dependencies.
docker compose up -d --no-deps --wait --wait-timeout 180 elastic
"${MIGRATION[@]}" up -d --wait --wait-timeout 180
```

The ES7 volume is declared `external: true`, so Compose fails if it does not exist instead of silently creating an empty source. For a bind-mounted ES7 data directory, adapt the migration file to use your original bind mount instead of the `elastic_7` named volume. Ensure the destination `nomad_oasis_elastic_9` volume is unused or empty, and is not the ES7 source volume.

The ES7 source joins the existing `nomad_oasis_network` as `elastic_7:9200`; ES9 remains the main stack's `elastic` service. If your main network has a custom name, export `ES_MIGRATION_NETWORK` with that name before starting ES7. Neither Elasticsearch service publishes a host port; the commands below run `curl` inside the containers. Keep the app, workers, and incoming traffic stopped until cutover.

#### 2. Copy Mapping and Create Index in ES9

Export the settings and mappings from ES7 and create the new index in the main stack's ES9 container.

Use the `INDEX` value recorded before stopping the app. The destination volume must be fresh and must not contain an existing index of that name.

```bash
set -o pipefail
: "${INDEX:?Set INDEX to the entries index name recorded before migration}"

# 1. Fetch settings and mapping from ES7 through its service container
"${MIGRATION[@]}" exec -T elastic_7 \
  curl -fsS "http://localhost:9200/${INDEX}/_settings?flat_settings=false" \
  > "/tmp/${INDEX}-settings.json"
"${MIGRATION[@]}" exec -T elastic_7 \
  curl -fsS "http://localhost:9200/${INDEX}/_mapping" \
  > "/tmp/${INDEX}-mapping.json"

# 2. Create the index on ES9 with replica count set to 0 and matching analysis settings
jq -n \
  --arg index "$INDEX" \
  --slurpfile settings "/tmp/${INDEX}-settings.json" \
  --slurpfile mapping "/tmp/${INDEX}-mapping.json" \
  '{
    settings: {
      number_of_shards:
        (($settings[0][$index].settings.index.number_of_shards // "1") | tonumber),
      number_of_replicas: 0,
      analysis: ($settings[0][$index].settings.index.analysis // {})
    },
    mappings: $mapping[0][$index].mappings
  }' | \
  docker compose exec -T elastic \
    curl -sS --fail-with-body -X PUT "http://localhost:9200/${INDEX}" \
    -H 'Content-Type: application/json' \
    --data-binary @- && \
  printf '\nCreated %s on ES9\n' "$INDEX"
```

#### 3. Reindex from ES7 to ES9

Send the reindex request to ES9, which reads from ES7 at `http://elastic_7:9200`:

```bash
set -o pipefail

jq -n \
  --arg index "$INDEX" \
  '{
    source: {
      remote: {host: "http://elastic_7:9200"},
      index: $index,
      size: 100
    },
    dest: {index: $index}
  }' | \
  docker compose exec -T elastic \
    curl -fsS -X POST \
    "http://localhost:9200/_reindex?wait_for_completion=true&refresh=true" \
    -H 'Content-Type: application/json' \
    --data-binary @- | jq .
```

Check that the response reports `"timed_out": false`, an empty `failures` array, and a `created` count equal to `total`. Do not proceed if the copy is incomplete.

#### 4. Verify Document Counts

Verify that the document count in ES9 matches ES7 while writes remain stopped:

```bash
echo "ES7 count:"
"${MIGRATION[@]}" exec -T elastic_7 \
  curl -fsS "http://localhost:9200/${INDEX}/_count" | jq .

echo "ES9 count:"
docker compose exec -T elastic \
  curl -fsS "http://localhost:9200/${INDEX}/_count" | jq .

echo "ES9 mapping property count:"
docker compose exec -T elastic \
  curl -fsS "http://localhost:9200/${INDEX}/_mapping" | \
  jq 'to_entries[0].value.mappings.properties | length'
```

#### 5. Finalize the Migration

Once verified:

1. Stop the temporary ES7 source, preserving its data volume and leaving ES9 running:

    ```bash
    "${MIGRATION[@]}" down
    ```

2. Verify the updated `docker-compose.yaml` and NOMAD configuration:

    - Set the main `elastic` service image to `docker.elastic.co/elasticsearch/elasticsearch:9.5.0`.
    - Add `xpack.security.enabled=false` to the main `elastic` service's `environment` list to disable Elasticsearch's built-in TLS and authentication, matching NOMAD's existing plain-HTTP connection configuration.
    - Set `container_name: nomad_oasis_elastic_9` for the main `elastic` service, as in the current template.
    - Keep its `elastic:/usr/share/elasticsearch/data` mount and set the top-level `volumes.elastic.name` to `nomad_oasis_elastic_9`, so it uses the migrated data.
    - Use the shared `x-nomad-environment` setting `NOMAD_ELASTIC_VERSION: ${NOMAD_ELASTIC_VERSION:-9}` and ensure `.env` or your shell does not override it with `7`. All NOMAD services must inherit it.
    - Preserve the entries index name recorded before migration.
    - Do not include `docker-compose.es-migration.yaml` when starting the application. The normal Compose file now references the migrated Docker volume through its `elastic` key. Do not delete the Docker volume itself.
    - Update the NOMAD images and other services for NOMAD 2.0 using the current distribution template; upgrading Elasticsearch alone does not upgrade NOMAD.

3. Disable remote copying and start your upgraded NOMAD Oasis. Remove `ELASTIC_REINDEX_REMOTE_WHITELIST` from `.env` too if you placed it there. Compose recreates ES9 with remote copying disabled, retaining the migrated volume:

    ```bash
    unset ELASTIC_REINDEX_REMOTE_WHITELIST
    docker compose up -d
    ```

4. Verify that searches work and that NOMAD uses the migrated index before allowing writes again. Retain the ES7 volume and backups until you no longer need rollback. To remove it later, use the actual old volume name recorded before migration (commonly `nomad_oasis_elastic`):

    ```bash
    docker volume rm nomad_oasis_elastic
    ```

### Option 2: Start with a fresh ES9 index and reindex uploads

In NOMAD, **MongoDB and the archive files (`.volumes/fs`) are the single source of truth**. This option starts Elasticsearch 9 with a fresh volume and reindexes all uploads from MongoDB and archive storage. It leaves the old ES7 volume untouched.

#### 1. Verify Backups and Stop the Old Stack

Complete the backup and configuration checks under **Before You Start**, then stop the old stack before editing Compose:

```bash
docker compose down
```

#### 2. Update Compose File

In `docker-compose.yaml`:

- Set `image: docker.elastic.co/elasticsearch/elasticsearch:9.5.0` under the `elastic` service.
- Add `xpack.security.enabled=false` to the `elastic` service's `environment` list to disable Elasticsearch's built-in TLS and authentication, matching NOMAD's existing plain-HTTP connection configuration.
- Set `container_name: nomad_oasis_elastic_9` for the `elastic` service.
- Use `NOMAD_ELASTIC_VERSION: ${NOMAD_ELASTIC_VERSION:-9}` in the shared `x-nomad-environment` anchor inherited by all NOMAD services. Remove any `.env` or shell override that still selects `7`.
- Preserve the entries index name recorded before migration.
- Update the NOMAD images and other services for NOMAD 2.0 using the current distribution template. The current template already includes the Elasticsearch settings above.
- Keep the `elastic:/usr/share/elasticsearch/data` service mount and change the top-level `volumes.elastic.name` to `nomad_oasis_elastic_9`:

    ```yaml
    volumes:
      # ... other volumes ...
      elastic:
        name: "nomad_oasis_elastic_9"
    ```

#### 3. Create the Fresh ES9 Volume and Start the App

Ensure `nomad_oasis_elastic_9` is unused or empty before continuing. Start the app and its dependencies without reopening access through the proxy or starting workers:

```bash
docker compose up -d --wait app
```

The old `nomad_oasis_elastic` volume remains available as a rollback until the migration is verified.

#### 4. Run the Indexing CLI Command

Wait until `app` and `elastic` are healthy, then trigger re-indexing across all uploads:

```bash
docker compose exec app python -m nomad.cli admin uploads index
```

#### 5. Verify and Resume Normal Operation

Check the CLI output for indexing errors and verify that the expected entries are searchable. Then start the remaining services:

```bash
docker compose up -d
```

Retain the old ES7 volume and backups until you no longer need rollback. To remove it later, use the actual old volume name recorded before migration (commonly `nomad_oasis_elastic`):

```bash
docker volume rm nomad_oasis_elastic
```
