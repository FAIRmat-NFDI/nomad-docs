# Migrate to NOMAD 2.0

## Elasticsearch Migration (v7.17 to v9.5)

Starting with **NOMAD 2.0**, the default Elasticsearch image has been changed from **Elasticsearch 7** to **Elasticsearch 9** (default container version `9.5.0`).

Because Elasticsearch 9 cannot read indices created with Elasticsearch 7 due to major Lucene version changes, existing data cannot be read directly from an old Elasticsearch 7 volume.

There are two migration options:

1. **Option 1: Reindex data directly from ES7 to ES9 (running two containers)** — Runs ES9 alongside ES7 and migrates the existing index through Elasticsearch's `_reindex` API. This is usually faster because it copies indexed documents without reprocessing archive files.
2. **Option 2: Start with a fresh ES9 index and reindex uploads** — Discards the ES7 search index and rebuilds it from MongoDB and the archive files (`.volumes/fs`), which are NOMAD's source of truth. This is simpler but can be considerably slower because NOMAD must read and index every upload again.

!!! note
    Previously, NOMAD maintained a separate materials index (`nomad_materials_v1` / `nomad_oasis_materials_v1`). This index is deprecated and dropped in NOMAD 2.0. **Only the entries index (`nomad_oasis_entries_v1` or `nomad_entries_v1`) needs to be migrated.**

!!! tip
    The steps below are for a Docker Compose deployment. If you run NOMAD on Kubernetes with the NOMAD Helm chart, follow [Kubernetes deployments (Helm chart)](#kubernetes-deployments-helm-chart) instead.

---

### Option 1: Reindex data directly from ES7 to ES9 (running two containers)

This approach runs a temporary Elasticsearch 9 container alongside your existing Elasticsearch 7 container, copies over the index mappings, and streams documents over the Docker network using Elasticsearch's remote `_reindex` API.

#### 1. Add the Temporary `nomad_oasis_elastic_9` Service

Add the `nomad_oasis_elastic_9` service and volume to your `docker-compose.yaml` (while keeping your existing `elastic` 7.x service running):

```yaml
services:
  # ... existing services ...

  nomad_oasis_elastic_9:
    restart: "no"
    image: docker.elastic.co/elasticsearch/elasticsearch:9.5.0
    container_name: nomad_oasis_elastic_9
    environment:
      - ES_JAVA_OPTS=-Xms512m -Xmx512m
      - cluster.routing.allocation.disk.threshold_enabled=true
      - cluster.routing.allocation.disk.watermark.flood_stage=1gb
      - cluster.routing.allocation.disk.watermark.low=4gb
      - cluster.routing.allocation.disk.watermark.high=2gb
      - discovery.type=single-node
      - xpack.security.enabled=false
      - reindex.remote.whitelist=elastic:9200
    ports:
      - "9201:9200"
    volumes:
      - nomad_oasis_elastic_9:/usr/share/elasticsearch/data
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:9200/_cluster/health?wait_for_status=yellow&timeout=2s"]
      interval: 2s
      timeout: 5s
      retries: 60
      start_period: 10s

volumes:
  # ... existing volumes ...
  nomad_oasis_elastic_9:
    name: "nomad_oasis_elastic_9"
```

Start the temporary ES9 container and wait for its health check to pass:

```bash
docker compose up -d --wait --wait-timeout 180 nomad_oasis_elastic_9
```

#### 2. Copy Mapping and Create Index in ES9

Export the settings and mappings from ES7 and create the new index in ES9 (port 9201).

The effective index name may come from configuration overrides rather than directly from `configs/nomad.yaml`. Read it from the running NOMAD app container:

!!! note
    Check effective entries index name by running `docker compose exec -T app python -c 'from nomad.config import config; print(config.elastic.entries_index)'`. It should be either `nomad_oasis_entries_v1` for a standard Oasis deployment or `nomad_entries_v1` if unset.

```bash
set -o pipefail

# Read the effective entries index name from NOMAD's configuration
INDEX="nomad_oasis_entries_v1"

# 1. Fetch settings and mapping from ES7 through its service container
docker compose exec -T elastic \
  curl -fsS "http://localhost:9200/${INDEX}/_settings?flat_settings=false" \
  > "/tmp/${INDEX}-settings.json"
docker compose exec -T elastic \
  curl -fsS "http://localhost:9200/${INDEX}/_mapping" \
  > "/tmp/${INDEX}-mapping.json"

# 2. Create the index on ES9 with replica count set to 0 and matching analysis settings
jq -n \
  --arg index "$INDEX" \
  --slurpfile settings "/tmp/${INDEX}-settings.json" \
  --slurpfile mapping "/tmp/${INDEX}-mapping.json" \
  '{
    settings: {
      number_of_shards:
        (($settings[0][$index].settings.index.number_of_shards // "1") | tonumber),
      number_of_replicas: 0,
      analysis: ($settings[0][$index].settings.index.analysis // {})
    },
    mappings: $mapping[0][$index].mappings
  }' | \
  curl -sS --fail-with-body -X PUT "http://localhost:9201/${INDEX}" \
    -H 'Content-Type: application/json' \
    --data-binary @- && \
  printf '\nCreated %s on ES9\n' "$INDEX"
```

#### 3. Reindex from ES7 to ES9

Trigger the remote reindex from the ES7 container (`http://elastic:9200`) into ES9:

```bash
set -o pipefail

jq -n \
  --arg index "$INDEX" \
  '{
    source: {
      remote: {host: "http://elastic:9200"},
      index: $index,
      size: 100
    },
    dest: {index: $index}
  }' | \
  curl -fsS -X POST \
    "http://localhost:9201/_reindex?wait_for_completion=true&refresh=true" \
    -H 'Content-Type: application/json' \
    --data-binary @- | jq .
```

#### 4. Verify Document Counts

Verify that the document count in ES9 matches ES7:

```bash
echo "ES7 count:"
docker compose exec -T elastic \
  curl -fsS "http://localhost:9200/${INDEX}/_count" | jq .

echo "ES9 count:"
curl -fsS "http://localhost:9201/${INDEX}/_count" | jq .

echo "ES9 mapping property count:"
curl -fsS "http://localhost:9201/${INDEX}/_mapping" | \
  jq 'to_entries[0].value.mappings.properties | length'
```

#### 5. Finalize the Migration

Once verified:

1. Stop the running containers:

    ```bash
    docker compose down
    ```

2. Update `docker-compose.yaml`:

    - Set the main `elastic` service image to `docker.elastic.co/elasticsearch/elasticsearch:9.5.0`.
    - Add `xpack.security.enabled=false` to the main `elastic` service's `environment` list to disable Elasticsearch's built-in TLS and authentication, matching NOMAD's existing plain-HTTP connection configuration.
    - Change the volume mount for `elastic` to use the migrated volume `nomad_oasis_elastic_9` (or replace the old volume).
    - Ensure `NOMAD_ELASTIC_VERSION: 9` is present in your NOMAD services (`app`, `worker`, etc.).
    - Remove the temporary `nomad_oasis_elastic_9` service definition from `docker-compose.yaml`.

3. Start your upgraded NOMAD Oasis:

    ```bash
    docker compose up -d
    ```

4. Remove the old ES7 volume if no longer needed:

    ```bash
    docker volume rm nomad_oasis_elastic
    ```

### Option 2: Start with a fresh ES9 index and reindex uploads

In NOMAD, **MongoDB and the archive files (`.volumes/fs`) are the single source of truth**. This option wipes the Elasticsearch volume, starts a fresh Elasticsearch 9 container, and reindexes all uploads from MongoDB and archive storage.

#### 1. Back Up MongoDB and File Storage

Before proceeding, run a MongoDB backup:

```bash
bash scripts/backup-mongo.sh
```

Ensure `.volumes/fs` is intact.

#### 2. Update Compose File

In `docker-compose.yaml`:

- Set `image: docker.elastic.co/elasticsearch/elasticsearch:9.5.0` under the `elastic` service.
- Add `xpack.security.enabled=false` to the `elastic` service's `environment` list to disable Elasticsearch's built-in TLS and authentication, matching NOMAD's existing plain-HTTP connection configuration.
- Ensure `NOMAD_ELASTIC_VERSION: 9` is set under the NOMAD container environment (`app`, `worker`, etc.).
- Keep the `elastic:/usr/share/elasticsearch/data` service mount and change the top-level `elastic.name` to `nomad_oasis_elastic_9`:

    ```yaml
    volumes:
      # ... other volumes ...
      elastic:
        name: "nomad_oasis_elastic_9"
    ```

#### 3. Create the Fresh ES9 Volume and Start Services

```bash
# Stop all containers
docker compose down

# Start the upgraded stack; Compose creates nomad_oasis_elastic_9
docker compose up -d
```

The old `nomad_oasis_elastic` volume remains available as a rollback until the migration is verified.

#### 4. Run the Indexing CLI Command

Wait until `app` and `elastic` are healthy, then trigger re-indexing across all uploads:

```bash
docker compose exec app python -m nomad.cli admin uploads index --parallel 4
```

!!! tip
    You can increase `--parallel` based on available CPU cores. For large deployments, add `--print-progress 10` to monitor ongoing progress.

#### 5. Remove the Old ES7 Volume

After verifying that the uploads are indexed correctly, remove the old ES7 volume:

```bash
docker volume rm nomad_oasis_elastic
```

### Kubernetes deployments (Helm chart)

NOMAD 2.0 is deployed with version 2.x of the [NOMAD Helm chart](https://github.com/FAIRmat-NFDI/nomad-helm-charts){:target="_blank" rel="noopener"}. Chart 1.x ran Elasticsearch 7 through the `elastic/elasticsearch` subchart (StatefulSet `elasticsearch-master`). Chart 2.x runs a single-node Elasticsearch 9 StatefulSet (`<release>-elasticsearch`) and configures NOMAD for it, so you do not need to set `NOMAD_ELASTIC_VERSION` yourself.

When you upgrade a chart 1.x release, Helm removes the `elasticsearch-master` StatefulSet but keeps its volume, the PersistentVolumeClaim `elasticsearch-master-elasticsearch-master-0`. NOMAD then starts on an empty Elasticsearch 9 index. The old ES7 data stays on that volume until you delete it, so you can copy it into Elasticsearch 9 (Option 1) or rebuild the index from MongoDB and the upload files instead (Option 2).

The commands below assume the release is called `nomad-oasis`, runs in the current namespace and was installed from the `nomad` Helm repository, as in the [deployment guide](../deploy.md#kubernetes). Replace `nomad-oasis` in the resource names if your release has a different name. The `elasticsearch-master` names do not depend on the release name.

#### Before you start

1. Back up MongoDB and the NOMAD file volumes. See [Backups](../administer.md#backups).

2. Read the name of the entries index from the running chart 1.x deployment. The chart names it after `nomad.config.mongo.db_name`, so it is usually `nomad_oasis_entries_v1`:

    ```bash
    kubectl exec deploy/nomad-oasis-app -- \
      python -c 'from nomad.config import config; print(config.elastic.entries_index)'
    ```

3. Check that the old Elasticsearch volume exists:

    ```bash
    kubectl get pvc elasticsearch-master-elasticsearch-master-0
    ```

    If it does not exist (for example because Elasticsearch persistence was disabled), there is no data to copy and you have to use Option 2.

4. Update your values file for chart 2.x. Several settings of the old subchart were renamed or dropped, and `helm upgrade` fails with an error message if one of them is still set. The [chart README](https://github.com/FAIRmat-NFDI/nomad-helm-charts/tree/main/charts/default#upgrading-from-chart-1x-elasticsearch-7---9){:target="_blank" rel="noopener"} lists all of them. For example, the `elasticsearch` block of the chart 1.x `kubernetes/values.yaml` from `nomad-distro-template`:

    ```yaml
    elasticsearch:
      replicas: 1
      minimumMasterNodes: 1
      clusterHealthCheckParams: "wait_for_status=yellow&timeout=1s"
      esConfig:
        elasticsearch.yml: |
          cluster.routing.allocation.disk.threshold_enabled: false
    ```

    becomes:

    ```yaml
    elasticsearch:
      settings:
        cluster.routing.allocation.disk.threshold_enabled: "false"
    ```

    Remove any `imageTag` override for Elasticsearch 7 as well.

5. Update the chart repository:

    ```bash
    helm repo update
    ```

#### Option 1: Reindex data from ES7 to ES9

This option upgrades the chart with NOMAD scaled down, starts a temporary Elasticsearch 7 on the old volume, and copies the entries index into the chart's Elasticsearch 9 with the remote `_reindex` API. NOMAD is unavailable until the copy is done.

1. Create a file `es-migration.yaml` that scales NOMAD down and allows Elasticsearch 9 to read from the temporary Elasticsearch 7 service:

    ```yaml
    nomad:
      app:
        replicaCount: 0
      worker:
        replicaCount: 0
      cpuworker:
        replicaCount: 0
      gpuworker:
        replicaCount: 0
    elasticsearch:
      settings:
        reindex.remote.whitelist: "nomad-oasis-es7:9200"
    ```

2. Upgrade the release with your values file and `es-migration.yaml`, and wait for Elasticsearch 9:

    ```bash
    helm upgrade nomad-oasis nomad/default -f values.yaml -f es-migration.yaml
    kubectl rollout status statefulset/nomad-oasis-elasticsearch --timeout=10m
    ```

3. Start a temporary Elasticsearch 7 on the old volume. Use the Elasticsearch 7 version your chart 1.x release ran (`7.17.3` unless you overrode `elasticsearch.imageTag`):

    ```bash
    kubectl apply -f - <<'EOF'
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: nomad-oasis-es7
    spec:
      replicas: 1
      strategy:
        type: Recreate
      selector:
        matchLabels:
          app: nomad-oasis-es7
      template:
        metadata:
          labels:
            app: nomad-oasis-es7
        spec:
          securityContext:
            fsGroup: 1000
            runAsUser: 1000
          containers:
            - name: elasticsearch
              image: docker.elastic.co/elasticsearch/elasticsearch:7.17.3
              env:
                # Must match the old cluster and node names stored in the data.
                - name: cluster.name
                  value: elasticsearch
                - name: node.name
                  value: elasticsearch-master-0
                - name: discovery.type
                  value: single-node
                - name: xpack.security.enabled
                  value: "false"
                # Avoids depending on the node's vm.max_map_count.
                - name: node.store.allow_mmap
                  value: "false"
                - name: ES_JAVA_OPTS
                  value: "-Xms1g -Xmx1g"
              ports:
                - containerPort: 9200
              readinessProbe:
                exec:
                  command:
                    - sh
                    - -c
                    - curl -fsS "http://localhost:9200/_cluster/health?wait_for_status=yellow&timeout=2s"
                periodSeconds: 10
              resources:
                requests:
                  cpu: 500m
                  memory: 2Gi
                limits:
                  memory: 2Gi
              volumeMounts:
                - name: data
                  mountPath: /usr/share/elasticsearch/data
          volumes:
            - name: data
              persistentVolumeClaim:
                claimName: elasticsearch-master-elasticsearch-master-0
    ---
    apiVersion: v1
    kind: Service
    metadata:
      name: nomad-oasis-es7
    spec:
      selector:
        app: nomad-oasis-es7
      ports:
        - port: 9200
    EOF

    kubectl rollout status deploy/nomad-oasis-es7 --timeout=10m
    ```

4. Forward Elasticsearch 7 to local port 9200 and Elasticsearch 9 to local port 9201 in the background. Run this and the next steps in the same shell, and keep the port-forwards running until the copy is verified:

    ```bash
    kubectl port-forward svc/nomad-oasis-es7 9200:9200 &
    kubectl port-forward svc/nomad-oasis-elasticsearch 9201:9200 &
    ```

5. Copy the settings and mappings and create the index on Elasticsearch 9:

    ```bash
    set -o pipefail

    # The entries index name from "Before you start"
    INDEX="nomad_oasis_entries_v1"

    curl -fsS "http://localhost:9200/${INDEX}/_settings?flat_settings=false" \
      > "/tmp/${INDEX}-settings.json"
    curl -fsS "http://localhost:9200/${INDEX}/_mapping" \
      > "/tmp/${INDEX}-mapping.json"

    jq -n \
      --arg index "$INDEX" \
      --slurpfile settings "/tmp/${INDEX}-settings.json" \
      --slurpfile mapping "/tmp/${INDEX}-mapping.json" \
      '{
        settings: {
          number_of_shards:
            (($settings[0][$index].settings.index.number_of_shards // "1") | tonumber),
          number_of_replicas: 0,
          analysis: ($settings[0][$index].settings.index.analysis // {})
        },
        mappings: $mapping[0][$index].mappings
      }' | \
      curl -sS --fail-with-body -X PUT "http://localhost:9201/${INDEX}" \
        -H 'Content-Type: application/json' \
        --data-binary @- && \
      printf '\nCreated %s on ES9\n' "$INDEX"
    ```

    !!! note
        If NOMAD 2.0 already ran against Elasticsearch 9 (for example because you upgraded without `es-migration.yaml`), it has created an empty index with the same name and the `PUT` fails. Delete it with `curl -fsS -X DELETE "http://localhost:9201/${INDEX}"` and run the step again.

6. Start the reindex from Elasticsearch 7 into Elasticsearch 9. Elasticsearch 9 reads from the temporary service inside the cluster (`http://nomad-oasis-es7:9200`). The reindex runs as a background task, so a long copy does not depend on the port-forward connection:

    ```bash
    TASK=$(jq -n \
      --arg index "$INDEX" \
      '{
        source: {
          remote: {host: "http://nomad-oasis-es7:9200"},
          index: $index,
          size: 100
        },
        dest: {index: $index}
      }' | \
      curl -fsS -X POST \
        "http://localhost:9201/_reindex?wait_for_completion=false" \
        -H 'Content-Type: application/json' \
        --data-binary @- | jq -r .task)

    # Wait for the task to finish, then show the result
    until curl -fsS "http://localhost:9201/_tasks/${TASK}" | jq -e .completed > /dev/null; do
      sleep 10
    done
    curl -fsS "http://localhost:9201/_tasks/${TASK}" | \
      jq '{error, total: .response.total, created: .response.created, failures: .response.failures}'
    curl -fsS -X POST "http://localhost:9201/${INDEX}/_refresh" > /dev/null
    ```

7. Verify that the document counts match:

    ```bash
    echo "ES7 count:"
    curl -fsS "http://localhost:9200/${INDEX}/_count" | jq .count

    echo "ES9 count:"
    curl -fsS "http://localhost:9201/${INDEX}/_count" | jq .count
    ```

8. Once verified, stop the port-forwards, remove the temporary Elasticsearch 7, and upgrade again without `es-migration.yaml`. This scales NOMAD back up and removes the `reindex.remote.whitelist` setting:

    ```bash
    kill %1 %2
    kubectl delete deployment/nomad-oasis-es7 service/nomad-oasis-es7
    helm upgrade nomad-oasis nomad/default -f values.yaml
    ```

9. Remove the old Elasticsearch 7 volume when you no longer need it:

    ```bash
    kubectl delete pvc elasticsearch-master-elasticsearch-master-0
    ```

#### Option 2: Start with a fresh ES9 index and reindex uploads

1. Upgrade the release and wait for Elasticsearch 9 and the NOMAD app:

    ```bash
    helm upgrade nomad-oasis nomad/default -f values.yaml
    kubectl rollout status statefulset/nomad-oasis-elasticsearch --timeout=10m
    kubectl rollout status deploy/nomad-oasis-app --timeout=15m
    ```

2. Reindex all uploads:

    ```bash
    kubectl exec deploy/nomad-oasis-app -- \
      python -m nomad.cli admin uploads index --parallel 4
    ```

    !!! tip
        You can increase `--parallel` based on the CPU available to the app pod. For large deployments, add `--print-progress 10` to monitor ongoing progress.

3. After verifying that the uploads are indexed correctly, remove the old Elasticsearch 7 volume:

    ```bash
    kubectl delete pvc elasticsearch-master-elasticsearch-master-0
    ```

#### Rolling back

As long as the `elasticsearch-master-elasticsearch-master-0` volume exists, you can return to the chart 1.x release and its Elasticsearch 7 data with `helm rollback`:

```bash
helm history nomad-oasis
helm rollback nomad-oasis <last chart 1.x revision>
```

For Option 1, delete the temporary `nomad-oasis-es7` Deployment and Service first, because only one Elasticsearch can use the volume at a time.
